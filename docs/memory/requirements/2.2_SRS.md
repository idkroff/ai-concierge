# 1. Введение

## 1.1. Назначение

Здесь собраны проверяемые требования к фиче «Память» Telegram-бота AI Concierge: по ним разрабатываем и тестируем. Цели и метрики — в 2.1_PRD, пользовательские истории — в 2.3_UserStories, трассировка — в 2.4_RTM.

## 1.2. Scope

Входит:

- хранение броней, которые сделал бот, и истории их изменений; список броней и карточка брони;
- бронь «как в прошлый раз»;
- поиск нужной брони по фразе пользователя, перенос и отмена с подтверждением и звонком;
- уточнение, если подходит несколько броней; отказ, если бронь уже прошла или её нет в памяти; статус результата только по ответу ресторана;
- автоматическое запоминание пожеланий с версиями и их подстановка в новые брони;
- просмотр, исправление, удаление и полная очистка памяти;
- учёт дневного лимита звонков для переноса и отмены;
- логирование событий для метрик PRD.

Не входит:

- перенос и отмена броней, сделанных без бота, и броней на прошедшие даты;
- интеграции с API ресторанов и агрегаторов;
- рекомендации ресторанов;
- сведения о здоровье и о других людях;
- другие поручения (врач, доставка);
- групповые брони и общая память нескольких пользователей.

## 1.3. Термины

| Термин | Значение |
|------|------------------|
| Бронь | Запись о брони, которую сделал бот: ресторан, телефон, дата, время, число гостей, имя пользователя из профиля, пожелания, статус, история изменений |
| Статус брони | `подтверждена`, `отклонена`, `не дозвонились` или `отменена` |
| Активная бронь | Бронь со статусом `подтверждена`, дата и время которой ещё не наступили |
| Пожелание (факт) | Постоянное пожелание пользователя одной из категорий: `зал` (тихий зал, веранда), `стол` (у окна), `время` (удобное время), `меню` (кухня, блюда). Хранится с источником и версиями |
| Тип поручения | `новая бронь`, `повтор` («как в прошлый раз»), `перенос`, `отмена` |
| Повторное поручение | Поручение типа `повтор`, `перенос` или `отмена` |
| Экран подтверждения | Сообщение бота с параметрами действия и двумя кнопками. Для новой брони и повтора — «Подтвердить» / «Не бронировать», для переноса и отмены — «Подтвердить» / «Не менять». Бот звонит только после «Подтвердить» |

# 2. Общее описание

## 2.1. Пользователи

| Класс | Описание |
|------|------------------|
| Пользователь | Студент или молодой специалист с Telegram-аккаунтом, прошедший `/start` и указавший номер телефона |
| Администратор | Разработчик из whitelist: сбрасывает лимиты, смотрит технические логи. К данным памяти доступа нет (NFR-09) |

## 2.2. Контекст системы

Фича расширяет то, что уже есть:

- `tg_bot` (Go) — интерфейс и сессии;
- `caller_service` — звонки через Asterisk и Yandex Realtime API, поиск организаций;
- YDB — пользователи и лимиты.

Добавляется:

- таблицы броней и пожеланий в YDB;
- фоновый обработчик сообщений на LLM;
- эмбеддинги для поиска по смыслу.

## 2.3. Допущения

- A-1. Рестораны соглашаются обсуждать перенос и отмену брони по телефону с ассистентом.
- A-2. Часовой пояс пользователя — Europe/Moscow.
- A-3. У пользователя один Telegram-аккаунт, идентификатор — Telegram `user_id`.

## 2.4. Зависимости

- D-1. `caller_service` запускает звонок с контекстом и возвращает итог (`farewell`, `abonent_hangup`, `timeout`, `cancelled`), транскрипт и признак согласия ресторана.
- D-2. LLM Yandex Cloud разбирает фразы пользователя и извлекает пожелания.
- D-3. Модель эмбеддингов Yandex Cloud.
- D-4. Telegram Bot API: inline-кнопки и команды.

## 2.5. Ограничения

- C-1. Инфраструктура — только Yandex Cloud (Kubernetes, YDB), как сейчас.
- C-2. Интерфейс — только Telegram-бот, текст и кнопки.
- C-3. Звонки — только через текущую телефонию (Asterisk, SIP-trunk).
- C-4. Персональные данные хранятся в РФ (152-ФЗ).

# 3. Функциональные требования

Приоритет: M — must, S — should.

## 3.1. Брони

| ID | Требование | Критерий приёмки | Пр. |
|---|---------------------|---------------------|---|
| FR-01 | После звонка по новой брони или повтору система сохраняет бронь: ресторан, телефон, дату, время, число гостей, имя пользователя, пожелания (если есть), статус и ссылку на итог звонка. Статус по итогу: ресторан согласился → `подтверждена`; разговор был, ресторан отказал → `отклонена`; `timeout` или разговор оборвался до согласия → `не дозвонились`; звонок отменён до разговора (`cancelled`) → бронь не сохраняется | 20 тестовых звонков, по 5 на каждый исход. Для первых трёх исходов в YDB ровно одна новая бронь, все поля, кроме пожеланий, заполнены, статус соответствует итогу в 15 из 15. Для `cancelled` новых броней 0 | M |
| FR-02 | Каждая попытка перенести или отменить бронь записывается в её историю: старые и новые параметры, время, итог звонка | После переноса 19:00 → 20:00 в истории есть запись с обоими значениями, временем и итогом; прежние записи не изменились | M |
| FR-03 | Команда `/bookings` показывает активные брони пользователя по возрастанию даты: ресторан, дата, время, гости, статус и кнопка «Подробнее» у каждой | Показаны все и только активные брони пользователя, по возрастанию даты, с датой и временем. Если их нет — «Активных броней нет» | M |
| FR-04 | Кнопка «Подробнее» открывает карточку брони со всеми полями и историей изменений, новые записи сверху | У брони, которую переносили 19:00 → 20:00, а потом 20:00 → 21:00, в карточке две записи, первой идёт «20:00 → 21:00»; у каждой есть дата изменения и итог звонка | M |
| FR-05 | Бронь «как в прошлый раз». Если во фразе есть ресторан из истории пользователя и слова «как в прошлый раз», «снова» или «опять», бот берёт ресторан, телефон и число гостей из последней брони в этом ресторане. Если дата не названа, бот её спрашивает. Если не названо время, бот спрашивает его и, если в памяти есть пожелание категории `время`, предлагает его кнопкой. Если ресторана нет в истории, бот отвечает «Не нашёл прошлых броней в „[ресторан]“. Напишите, когда и на сколько человек бронировать» | На «забронируй как в прошлый раз в Пушкине на пятницу в 19:00» экран подтверждения содержит ресторан, телефон и 2 гостей из прошлой брони, бот о них не спрашивает. Без времени — вопрос «На какое время?» и кнопка «19:00», если такой факт есть. Для ресторана без истории — ответ по шаблону, звонков 0 | M |

## 3.2. Перенос и отмена

| ID | Требование | Критерий приёмки | Пр. |
|---|---------------------|---------------------|---|
| FR-06 | Бот находит нужную бронь по фразе. Признаки: название ресторана или тип заведения («ресторан», «кафе», «бар»), дата (число, «сегодня», «завтра», день недели), время. Бронь подходит, если совпадают все признаки, названные во фразе. Время после «на» в команде переноса («перенеси на 21:00») — новое значение, а не признак поиска. Порядок: ровно одна подходящая активная бронь → выбрана она; две и больше → FR-07; активных нет, но есть прошедшая со статусом `подтверждена` → FR-08; иначе → FR-09 | Для каждой из 4 веток тест даёт ожидаемый ответ. На эталонном наборе из 50 фраз ≥ 90% верных ответов (подробнее — NFR-05) | M |
| FR-07 | Если подходят две активные брони или больше, бот спрашивает «Какую бронь?» и показывает их кнопками («ресторан, дата, время»). До выбора бот не звонит. После выбора показывает экран подтверждения по выбранной брони | Кнопка на каждую подходящую бронь; до выбора звонков 0; после выбора на экране параметры выбранной брони | M |
| FR-08 | Если подходящая бронь уже прошла, бот отвечает «Бронь в „[ресторан]“ на [дата] уже прошла. Переносить и отменять можно только будущие брони» и не звонит | Ответ совпадает с шаблоном; звонков 0; лимит не уменьшился | M |
| FR-09 | Если подходящей брони нет (сделана без бота, уже отменена, отклонена или принадлежит другому пользователю), бот отвечает «Не нашёл активной брони по вашему описанию. Ваши брони: /bookings. Если нужно забронировать заново, напишите, куда, когда и на сколько человек» и не звонит | Ответ совпадает с шаблоном; звонков 0; лимит не уменьшился | M |
| FR-10 | Перенос. Бот вычисляет новые параметры (относительные, вроде «на час позже», — от текущих) и показывает экран «было → станет» с гостями и пожеланиями. После «Подтвердить» звонит в ресторан, после «Не менять» ничего не делает | Для брони на 19:00 и фразы «на час позже» экран показывает «19:00 → 20:00». До «Подтвердить» звонков 0. После «Подтвердить» и согласия ресторана бронь на 20:00, пользователь получает обновлённую карточку. После «Не менять» звонков 0, бронь та же | M |
| FR-11 | Отмена. Бот показывает экран с параметрами брони. После «Подтвердить» звонит; если ресторан согласился, статус брони — `отменена`. После «Не менять» ничего не делает | После «Подтвердить» и согласия ресторана статус `отменена`, брони нет в `/bookings`, пользователь получает «Бронь отменена». После «Не менять» звонков 0, статус `подтверждена` | M |
| FR-12 | Если ресторан не согласился на перенос или отмену, бронь не меняется, в историю пишется неудачная попытка, а пользователь получает «Перенос не подтверждён: [причина]» или «Отмена не подтверждена: [причина]». Причина: `timeout` → «ресторан не ответил»; разговор оборвался до согласия → «разговор прервался»; ресторан отказал → «ресторан отказал ([короткий пересказ причины из итога звонка])» | Проверены все 6 сочетаний (2 действия × 3 причины): параметры и статус брони не изменились, в истории есть неудачная попытка, сообщение начинается с нужной фразы и содержит нужную причину; для отказа в скобках непустой текст | M |

## 3.3. Пожелания

| ID | Требование | Критерий приёмки | Пр. |
|---|---------------------|---------------------|---|
| FR-13 | Фоновый обработчик читает каждое текстовое сообщение и извлекает постоянные пожелания категорий `зал`, `стол`, `время`, `меню`. Постоянное — сказанное со словами вроде «всегда», «обычно», «люблю», «предпочитаю», «теперь всегда». Разовые пожелания к конкретной брони («в этот раз на веранде»), сведения о здоровье и о других людях не извлекаются | Из «Я всегда прошу тихий зал» извлекается «тихий зал», категория `зал`. Из «в этот раз посадите на веранду» и «у меня аллергия на орехи» факты не создаются. На размеченном наборе из 100 сообщений precision ≥ 90%, recall ≥ 70% (NFR-06) | M |
| FR-14 | Извлечённый факт сразу становится активным, бот ничего не спрашивает. Бот пишет «Запомнил: [факт]» с кнопкой «Забыть». «Забыть» удаляет эту версию факта, и активной снова становится предыдущая, если она была. Для дубля (FR-15) сообщение не отправляется | После «Я всегда прошу тихий зал» факт есть в `/memory`, пользователь получил «Запомнил: тихий зал». После «Забыть» факта нет в `/memory` и в следующей брони он не подставляется. Если «Забыть» нажато после замены «тихий зал» → «веранда», активен снова «тихий зал» | M |
| FR-15 | Дубли не создаются. Дубль — та же категория и то же значение после нормализации (нижний регистр, лемматизация) или косинусная близость эмбеддингов ≥ 0,90. В категориях `зал`, `стол`, `время` новое значение заменяет активное как новая версия, старая версия остаётся в истории. В категории `меню` новые значения добавляются | Повторное «люблю тихий зал» не меняет число фактов. «Теперь всегда хочу на веранду» делает активной версию 2 «веранда» (категория `зал`), версия 1 «тихий зал» есть в истории | M |
| FR-16 | В новой брони и повторе активные факты категорий `зал`, `стол`, `меню` показываются на экране подтверждения строкой «Учту: …» и передаются в контекст звонка. Кнопка «Убрать [факт]» исключает факт из этой брони, но не из памяти | На экране есть «Учту: тихий зал», в контексте звонка — «тихий зал». После «Убрать тихий зал» в контексте звонка его нет, а в `/memory` он остался | M |
| FR-17 | Команда `/memory` показывает активные факты: категорию, значение, дату и источник — цитату сообщения (до 100 символов, дальше «…») или «исправлено вручную» | Список совпадает с активными фактами в YDB, у каждого есть категория, дата и источник. Факт из сообщения длиной 150 символов показан с цитатой из 100 символов и «…». Если фактов нет — «Я пока ничего о вас не запомнил» | M |
| FR-18 | В `/memory` у каждого факта есть кнопки «Исправить» и «Удалить». «Исправить» сохраняет введённое значение как новую версию с источником «исправлено вручную». «Удалить» стирает факт вместе со всеми версиями | После «Исправить» → «второй этаж» в `/memory` показан «второй этаж» с источником «исправлено вручную». После «Удалить» факта и его версий нет в YDB, в следующей брони он не подставляется | M |
| FR-19 | Команда `/forget` показывает «Удалю всё, что помню о вас: пожелания и историю броней. Активных броней: N — после очистки я не смогу их перенести или отменить» и кнопки «Удалить всё» / «Не удалять». «Удалить всё» стирает факты со всеми версиями, эмбеддинги, брони с историей и транскрипты звонков пользователя, а в логах событий заменяет его `user_id` обезличенным идентификатором | После «Удалить всё» `/memory` и `/bookings` пусты, следующая бронь создаётся без пожеланий. После «Не удалять» число фактов и броней не изменилось | M |
| FR-20 | У каждого факта хранится источник (ссылка на сообщение или отметка «исправлено вручную») и дата создания | У всех фактов в YDB заполнены `source_ref` и `created_at` | M |

## 3.4. Лимит звонков

| ID | Требование | Критерий приёмки | Пр. |
|---|---------------------|---------------------|---|
| FR-21 | Каждый запущенный звонок — новая бронь, повтор, перенос или отмена — списывает 1 звонок из дневного лимита (3 в сутки) при любом итоге. Если лимит исчерпан, бот вместо экрана подтверждения отвечает «Достигнут дневной лимит звонков (3). Попробуйте завтра» и не звонит. Ответы FR-07 — FR-09 лимит не тратят | После трёх звонков, включая один с итогом `timeout`, запрос на перенос получает ответ по шаблону, звонков 0. Отказ по FR-08 или FR-09 не меняет счётчик | M |

## 3.5. Измерение

| ID | Требование | Критерий приёмки | Пр. |
|---|---------------------|---------------------|---|
| FR-22 | Система пишет события с `user_id` и временем: `message_received`, `button_pressed`, `task_started` (первое сообщение поручения), `task_confirmed` (нажато «Подтвердить»), `call_started`, `call_result` (с признаком согласия), `preference_saved`, `preference_forgotten`, `preference_applied`, `preference_excluded`, `memory_cleared`, `response_latency_ms`, `llm_call`. У событий поручения есть `task_id`, `task_type` и, если поручение связано с бронью, `booking_id` (`новая бронь`, `повтор`, `перенос`, `отмена`); у `response_latency_ms` — вид ответа (`экран подтверждения` или `другое`); у `llm_call` — назначение (`память` или `разбор фразы`) | В сценарии переноса события идут в порядке `message_received` → `task_started` → `task_confirmed` → `call_started` → `call_result`, у всех есть `user_id`, `task_id`, `task_type`, время. По событиям тестового прогона считаются M-1, P-1, P-2, G-2, G-3 и p95 экрана подтверждения из G-4. Запрос «`call_started` без предшествующего `task_confirmed`» возвращает 0 строк | M |

# 4. Нефункциональные требования

| ID | Категория | Требование | Критерий приёмки | Пр. |
|---|------|------------------|------------------|---|
| NFR-01 | Производительность | Любой экран подтверждения (новая бронь, повтор, перенос, отмена) появляется не позже 3 с после сообщения пользователя в 95% случаев.
